# 完成未读是行内标记，不是第四个看板

「完成未读」——会话跑完一轮、当前未被选中、且此后没打开过——**不单独成栏**，而是作为行内标记叠加在状态记号上，并在每块看板的标题里附上计数。

## 为什么不并入「待我决策」

决策栏的含义是「我不回它就不前进」。这是该栏唯一的意义，也是 0.3.0 一次真实缺陷修复的结果：当时把团队待办误当决策信号，让一个六天前已完成的会话长期钉在决策板上。混入「跑完没看」会让这个数字变成混合口径，而它的价值恰恰在于精确。

## 为什么不做成第四栏

现有三栏都由**可持久推导的事实**构成，重新打开程序后结论不变。而 `completionUnread` 由平台以内存态维护：它在观察 `running: true → false` 时置位，刷新后清空（首次加载只把 `running` 写进基线，不补发完成事件）。

把内存态与事实并列成四栏，会让同一栏在不同会话里表示不同性质的东西——一栏为空时，读的人无法区分「确实没有」「还没观察到」「刷新过」。作为提醒标记则不承担这个承诺。

## 额外代价

加一栏要改约 18 处，其中 6 处是手写字面量（Loader schema、折叠状态的解析与序列化、看板构建、入口的三组计数）；漏改任一处会让旧 `localStorage` 直接失效。而标记只需渲染层改动，并且不触碰「一个会话恰好落一栏」这条被测试锁定的契约。

## Consequences

- 完成未读与判定状态**可以同时存在**：一行既可能在等人回答，又带着未读的完成结果。两者叠加显示，不互相替换。
- 它读的是平台发布的 `useSessionStatus`，而不是自建已读表，因此不会与侧栏的绿色完成点出现不一致。
- 平台在会话重新运行或成为主视图时清除该标记，所以它不表示永久未读历史。
